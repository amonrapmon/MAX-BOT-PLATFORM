# Референсная архитектура нативной интеграции MAX + Dikidi

## Статус документа

Этот документ является техническим приложением к [предложению совместного пилота MAX + Dikidi](../../MAX-DIKIDI-INTEGRATION-PROPOSAL.md).

Он описывает референсную архитектуру клиентского бота, интеграционного API-слоя и механизмов надёжности. Документ рассчитан на backend/platform-команду Dikidi и не является описанием внутренней физической инфраструктуры Dikidi.

Транспортные требования опираются на [MAX Bot Platform Standard v1](../../STANDARD.md). Стандарт определяет проверенные поведенческие контракты для long polling, состояния Redis, дедупликации, очередей, повторных попыток, наблюдаемости и корректного завершения процессов.

## 1. Scope и границы

В область документа входят:

- клиентский бот MAX;
- транспортный runtime;
- интеграционный gateway между MAX и Dikidi;
- идентификация пользователя по подтверждённому телефону;
- получение и отображение записей;
- напоминания;
- подтверждение визита;
- запрос переноса;
- запрос отмены;
- очереди, идемпотентность и повторные попытки;
- безопасность, наблюдаемость и масштабирование;
- переход от текущего long polling к целевой webhook-модели;
- передача решения для развёртывания в инфраструктуре Dikidi.

В область документа не входят:

- администраторский бот;
- управление сотрудниками;
- отчёты;
- прайсы;
- внутренний интерфейс компаний;
- финансовая модель проекта;
- точный размер закрытого пилота;
- окончательный выбор языка промышленной реализации;
- юридическая квалификация ролей без участия Dikidi.

## 2. Архитектурные принципы

### 2.1. Отделение транспорта от продуктовой логики

Клиентские сценарии не должны зависеть от конкретного MAX SDK, polling marker, Redis-ключей транспорта или способа получения событий.

```text
Application handlers
        │
        │ stable application port
        ▼
MAX Bot Runtime
        │
        │ transport adapter
        ▼
MAX API
```

Это позволяет заменить long polling на webhook без переписывания сценариев идентификации, получения записей, напоминаний и действий пользователя.

### 2.2. Dikidi остаётся источником истины

Клиентские карточки, записи, услуги, мастера, компании, филиалы и окончательное состояние визита принадлежат Dikidi.

Клиентский контур хранит только техническое состояние, необходимое для:

- идентификации пользователя MAX;
- доставки сообщений;
- идемпотентности операций;
- работы очередей;
- напоминаний;
- минимального аудита.

### 2.3. Обработка строится вокруг повторяемости

Система не предполагает, что сеть, MAX или Dikidi всегда возвращают ответ с первой попытки. Любая операция проектируется с учётом:

- повторной доставки входящего события;
- повторного нажатия кнопки;
- перезапуска процесса;
- потери ответа после фактического выполнения операции;
- временной недоступности внешнего API;
- конкурирующих workers.

### 2.4. Надёжность определяется поведением, а не языком

TypeScript, Python, Go, PostgreSQL и Redis являются вариантами реализации, а не обязательной частью продукта.

Обязательными остаются поведенческие контракты:

- stable event identity;
- at-least-once processing;
- deduplication;
- durable queue;
- idempotent publication;
- bounded retries;
- lease fencing;
- dead letter;
- graceful shutdown;
- health states;
- structured observability;
- controlled recovery.

## 3. Целевая схема компонентов

```text
┌──────────────────────┐
│ Пользователь MAX     │
└──────────┬───────────┘
           │ события, контакты, кнопки
           ▼
┌──────────────────────┐
│ Клиентский бот MAX   │
│ application handlers │
└──────────┬───────────┘
           │ нормализованные команды
           ▼
┌───────────────────────────────┐
│ Надёжный транспортный runtime │
│ inbound state / outbound jobs │
└──────────┬────────────────────┘
           │ внутренний API-контракт
           ▼
┌───────────────────────────────┐
│ Интеграционный gateway        │
│ identity / appointments /     │
│ actions / normalization       │
└──────────┬────────────────────┘
           │ официальный API
           ▼
┌──────────────────────┐
│ Dikidi               │
│ source of truth      │
└──────────────────────┘
```

### 3.1. Клиентский бот

Отвечает за:

- стартовый пользовательский сценарий;
- отображение первого сообщения;
- передачу гиперссылок на документы Dikidi;
- запрос собственного контакта MAX;
- отображение найденных записей;
- группировку записей по компаниям;
- построение кнопок действий;
- возврат понятного результата пользователю.

Бот не должен:

- работать с внутренней БД Dikidi;
- содержать transport retry policy;
- напрямую отправлять сообщения в MAX API из handler;
- управлять polling marker;
- создавать собственную модель компаний и филиалов;
- считать локальное состояние окончательным состоянием записи.

### 3.2. Транспортный runtime

Отвечает за:

- получение событий MAX;
- нормализацию событий в платформенные типы;
- stable `event_id`;
- ownership входящего потока;
- inbound deduplication;
- durable outbound queue;
- rate limiting;
- retries и `Retry-After`;
- leases и fencing;
- acceptance receipts;
- dead letter;
- graceful shutdown;
- structured logs, health и metrics.

### 3.3. Интеграционный gateway

Отвечает за:

- поиск записей по подтверждённому телефону;
- агрегацию результатов из нескольких компаний и филиалов;
- нормализацию ответа API Dikidi;
- передачу подтверждения;
- передачу запроса переноса;
- передачу запроса отмены;
- контроль текущего состояния записи;
- классификацию ошибок;
- идемпотентность изменяющих операций;
- возврат нормализованного результата клиентскому боту.

Gateway должен быть stateless настолько, насколько это позволяет официальный API-контракт Dikidi.

### 3.4. Техническое состояние

Для промышленного контура достаточно минимального состояния:

```text
MAX user ID
MAX chat ID
bot instance ID
нормализованный подтверждённый телефон
момент подтверждения контакта
версия согласия при необходимости
idempotency keys
inbound event state
outbound jobs
leases
acceptance receipts
reminder state
минимальный audit trail
```

Не требуется постоянно хранить:

```text
полную клиентскую карточку
историю посещений
услуги и прайс
мастеров
филиалы
финансовые данные
полный текст переписки
полный raw payload MAX или Dikidi
```

## 4. Потоки взаимодействия

## 4.1. Первый запуск и передача контакта

```text
1. Пользователь запускает клиентского бота.
2. Бот показывает назначение сервиса.
3. В тексте размещаются гиперссылки на документы Dikidi.
4. Пользователь нажимает «Передать номер телефона».
5. MAX передаёт contact payload.
6. Runtime нормализует событие и назначает stable event ID.
7. Handler проверяет, что контакт принадлежит отправителю.
8. Телефон нормализуется.
9. Gateway получает или обновляет техническую идентичность пользователя.
10. Пользователь получает подтверждение готовности сервиса.
```

Проверка self-contact обязательна:

```text
contact_user_id == max_user_id
```

Ручной ввод произвольного телефона не используется как доверенный способ идентификации.

## 4.2. Получение предстоящих записей

```text
1. Пользователь запрашивает «Мои записи».
2. Handler получает подтверждённый нормализованный телефон.
3. Gateway обращается к API Dikidi.
4. API возвращает клиентские карточки и связанные записи.
5. Gateway удаляет дубли одной записи.
6. Записи группируются по компании и филиалу.
7. Handler формирует пользовательский ответ.
8. Ответ публикуется как durable outbound job.
9. Sender worker доставляет сообщение в MAX.
10. Runtime сохраняет acceptance receipt.
```

Пользователь не привязан к одной компании. Один номер телефона может соответствовать нескольким клиентским карточкам и нескольким компаниям.

Рекомендуемый ключ дедупликации записи:

```text
(dikidi_company_id, appointment_id)
```

Если модель филиалов использует отдельный устойчивый идентификатор, он включается в нормализованный объект записи, но не заменяет идентификатор компании без подтверждения API-контракта.

## 4.3. Напоминание

```text
1. Планировщик определяет записи, попадающие в окно напоминания.
2. Для записи определяется нормализованный телефон клиента.
3. По телефону находятся все подтверждённые MAX recipients.
4. Для каждого recipient создаётся reminder identity.
5. Создаётся idempotent outbound job.
6. Sender worker отправляет напоминание.
7. MAX acceptance фиксируется отдельно от фактического прочтения.
```

Одинаковое напоминание одному recipient не должно создаваться повторно.

Типовой idempotency key может включать:

```text
bot_instance_id
recipient_id
dikidi_company_id
appointment_id
appointment_start
reminder_window
```

## 4.4. Действие пользователя

```text
1. Пользователь нажимает кнопку.
2. Runtime нормализует callback.
3. Проверяется stable event ID и deduplication state.
4. Проверяется принадлежность reminder текущему MAX user.
5. Фиксируется выбор пользователя.
6. Gateway читает актуальное состояние записи.
7. Действие передаётся в integration endpoint.
8. Результат нормализуется.
9. Пользователю создаётся durable response job.
10. Итог операции сохраняется в минимальном audit trail.
```

Допустимые действия:

```text
confirmed
reschedule_requested
cancel_requested
```

Публичная формулировка интеграции:

> Выбор пользователя передаётся в интеграционный endpoint изменения состояния записи. Операция выполняется с контролем текущего состояния, защитой от повторного выполнения и фиксацией результата доставки.

Текущая пилотная реализация delivery adapter и целевой официальный API-контракт должны оставаться разными понятиями. Документ не утверждает, что наблюдаемый пилотный endpoint является публичным официальным API Dikidi.

## 5. Модель идентификации

### 5.1. Глобальная идентичность клиента

Клиент определяется не парой «компания + пользователь MAX», а подтверждённым номером телефона пользователя MAX.

```text
MAX identity
├── max_user_id
├── max_chat_id
├── bot_instance_id
└── phone_normalized
```

Компания не является частью постоянной идентичности клиента в боте.

Это позволяет одному пользователю видеть записи во всех компаниях и филиалах, где его номер присутствует в клиентской карточке.

### 5.2. Несколько карточек с одним телефоном

Одинаковый телефон может находиться:

- в нескольких компаниях;
- в нескольких филиалах;
- в нескольких клиентских карточках одной компании;
- у нескольких подтверждённых получателей MAX, если бизнес-правила допускают общий контакт.

Gateway не должен считать телефон глобально уникальным идентификатором клиентской карточки Dikidi. Телефон является ключом поиска, а устойчивый appointment identity строится на идентификаторах Dikidi.

### 5.3. Отсутствие совпадения

Если по телефону не найдены записи, пользователь получает нейтральный ответ без раскрытия существования иных карточек или компаний.

Пример нормализованного результата:

```text
Записей по подтверждённому номеру сейчас не найдено.
```

API не должен позволять использовать бот как произвольный интерфейс перебора телефонов.

## 6. Зеркальная модель пилота и целевой API

## 6.1. Назначение пилотной модели

До получения официального API-доступа была построена зеркальная модель фактически наблюдаемого интеграционного контракта Dikidi.

Она воспроизводит доступные сущности, идентификаторы и отношения без введения собственных бизнес-значений и без произвольного переименования доменных полей.

Типовая логическая модель:

```text
company
├── clients
├── appointments
│   ├── appointment_clients
│   ├── appointment_services
│   ├── appointment_masters
│   └── appointment_resources
├── services
├── masters
└── resources
```

Названия сущностей, идентификаторов и связей основаны на фактически наблюдаемом интеграционном контракте. Внутренняя реализация и физическая схема хранения Dikidi могут отличаться.

### 6.2. Почему зеркало не является целевой архитектурой

Пилотная PostgreSQL-модель позволила:

- изучить структуру данных;
- проверить сценарии идентификации;
- разработать поиск записей;
- воспроизводить ошибки;
- тестировать напоминания и пользовательские действия;
- подтвердить архитектурные границы.

Она не предлагается как промышленная БД для всей клиентской базы Dikidi.

### 6.3. Целевая модель

После получения официального API-доступа:

```text
клиентские данные → читаются из Dikidi
состояние записи → изменяется в Dikidi
окончательный результат → определяется Dikidi
локально → хранится только техническое состояние бота
```

Локальный кеш возможен как ограниченная техническая оптимизация, но не как второй источник истины.

## 7. Транспорт: текущий long polling

Текущая пилотная реализация использует long polling.

### 7.1. Polling marker

Runtime восстанавливает последний сохранённый marker до первого запроса событий.

Marker продвигается только после успешной обработки полного batch.

```text
poll batch
→ normalize
→ handle every event
→ persist completion states
→ commit next marker
```

Если один event завершился ошибкой, новый marker не сохраняется. Событие должно оставаться доступным для replay.

### 7.2. Единственный polling owner

Для одной runtime identity и bot token допускается только один активный polling owner.

Ownership реализуется через lease.

При потере lease runtime прекращает новые poll requests, что предотвращает split-brain и конкурирующее продвижение marker.

### 7.3. Дедупликация входящих событий

Каждый поддерживаемый тип update преобразуется в deterministic stable event ID.

```text
same protocol event
→ same event_id
```

Завершённый duplicate не доходит до application handler повторно.

Неуспешное событие не помечается завершённым и может быть воспроизведено после восстановления.

## 8. Эволюция транспорта: webhook

Webhook пока не реализован в текущем пилоте и не заявляется как готовая функция.

Архитектурно переход уже предусмотрен через разделение transport adapter и application port.

```text
Long Polling Adapter ─┐
                      ├→ BotEvent → Application handlers
Webhook Adapter     ──┘
```

### 8.1. Целевая webhook-схема

```text
MAX webhook
    ↓
Ingress / Load Balancer
    ↓
проверка подлинности и структуры
    ↓
назначение stable event ID
    ↓
durable inbound queue
    ↓
быстрое подтверждение приёма
    ↓
пул workers
    ↓
integration gateway
    ↓
API Dikidi
```

Webhook ingress не должен выполнять полный бизнес-сценарий внутри HTTP-запроса.

Его ответственность ограничивается:

- валидацией запроса;
- stable event identity;
- долговечной фиксацией события;
- быстрым подтверждением приёма;
- передачей работы независимым workers.

### 8.2. Преимущества webhook-модели

- stateless ingress instances;
- балансировка входящих запросов;
- независимое масштабирование ingress и workers;
- backpressure через очередь;
- изоляция тяжёлых операций;
- контролируемый concurrency;
- обновление workers без остановки ingress;
- возможность отдельного autoscaling по глубине очереди;
- более естественное распределение нагрузки при большом числе событий.

Webhook не заменяет дедупликацию, очереди и идемпотентность. Без них он только ускоряет доставку повторных и частично обработанных событий к application layer.

## 9. Исходящие сообщения и durable queue

Application handler не отправляет сообщения напрямую в MAX API.

```text
handler
→ enqueue outbound job
→ durable state
→ sender worker
→ MAX API
→ acceptance receipt
```

### 9.1. Идемпотентная публикация

Публикация одинакового outbound idempotency key создаёт не более одной job identity.

Повторный handler execution не должен размножать сообщения.

### 9.2. Claim и lease

Sender worker получает временный lease на job.

Только текущий владелец lease может:

- продлить claim;
- завершить job;
- назначить retry;
- переместить job в dead letter.

Устаревший worker после потери lease не может перезаписать решение нового владельца.

### 9.3. Acceptance receipt

Успешный ответ MAX с message ID фиксируется как:

```text
accepted_by_max
```

Это не должно называться «доставлено пользователю» или «прочитано».

Receipt не должен содержать текст сообщения, контактные данные, токены или raw response.

## 10. Taxonomy ошибок

Ошибки классифицируются до выбора дальнейшего действия.

| Класс | Пример | Поведение |
|---|---|---|
| Временная транспортная | timeout, reset, 502, 503 | bounded retry |
| Rate limited | 429, `Retry-After` | отложенный retry |
| Постоянная техническая | неверный токен, неподдерживаемый контракт | dead letter или unhealthy |
| Ошибка конфигурации | отсутствующий secret, неверный runtime ID | fail fast до обработки |
| Конфликт состояния | потерян lease, изменился owner | остановка устаревшего worker |
| Бизнес-отказ | запись уже отменена, действие запрещено | без технического retry |
| Неизвестная | новый непредусмотренный ответ | ограниченные retries, затем изоляция |

### 10.1. Retry policy

Для временных ошибок применяется bounded exponential backoff с jitter.

Каноническая последовательность транспортного runtime:

```text
1s → 2s → 4s → 8s → 10s + jitter
```

Если внешний API возвращает `Retry-After`, используется большее значение между вычисленным backoff и `Retry-After`, с разумным верхним пределом.

### 10.2. Dead letter

В dead letter попадают:

- permanent errors;
- исчерпавшие лимит attempts jobs;
- incompatible contract responses;
- poison events, которые невозможно безопасно обработать автоматически.

Dead letter сохраняет технический контекст операции, но не должен становиться архивом персональных данных.

### 10.3. Бизнес-ошибки

Бизнес-ошибка не считается технической недоступностью.

Примеры:

```text
запись уже подтверждена
запись уже отменена
время записи изменилось
операция больше недоступна
пользователь не связан с записью
```

Такие ответы нормализуются и возвращаются пользователю без бессмысленного технического retry.

## 11. Failure matrix

| Сценарий | Реакция системы | Сохраняемая гарантия |
|---|---|---|
| MAX временно недоступен | backoff + jitter, без потери job | исходящая job остаётся durable |
| MAX возвращает 429 | учитывается `Retry-After` | ограничение платформы не обходится лавиной запросов |
| Poll request завершился ошибкой | marker не продвигается | события не пропускаются |
| Batch обработан частично | marker остаётся прежним | неуспешное событие доступно для replay |
| Событие пришло повторно | stable event ID + completed-state dedupe | handler не выполняется второй раз |
| Handler завершился ошибкой | event не помечается completed | возможен безопасный replay |
| Процесс перезапущен | marker, queue и leases восстанавливаются | принятая работа не зависит от жизни процесса |
| Два poller запущены одновременно | только один получает ownership | отсутствует split-brain polling |
| Worker умер после claim | lease истекает, job доступна другому worker | работа не остаётся навечно захваченной |
| Старый worker продолжил выполнение | fencing запрещает terminal transition | результат нового владельца не перезаписывается |
| Redis недоступен | новые polls и claims приостанавливаются | система не работает без durable state вслепую |
| API Dikidi отвечает timeout | retry по политике временных ошибок | операция не теряется после первой неудачи |
| API Dikidi отвечает 429 | отложенный retry | соблюдаются лимиты Dikidi |
| Dikidi вернула бизнес-отказ | retry не выполняется | пользователю возвращается актуальный результат |
| Dikidi изменила запись, но ответ потерян | idempotency key или чтение текущего состояния | исключается слепое повторное изменение |
| Изменился API-контракт | операция изолируется, health/alert | несовместимые данные не интерпретируются молча |
| Job исчерпала attempts | dead letter | очередь не содержит бессмертных poison jobs |
| SIGTERM во время работы | прекращаются новые polls/claims, активная работа drain/release | deployment не обрывает работу неконтролируемо |
| Webhook доставлен повторно | stable event ID + durable dedupe | бизнес-действие не размножается |
| Проблемная компания создаёт всплеск | per-company limits и backpressure | остальные компании продолжают обслуживаться |

## 12. Частично выполненные операции Dikidi

Самый рискованный сценарий изменяющей операции:

```text
Dikidi приняла изменение
→ соединение оборвалось
→ gateway не получил итоговый ответ
```

Система не должна слепо повторять команду.

Предпочтительный порядок:

1. Использовать официальный idempotency key, если API его поддерживает.
2. Сохранить operation identity до отправки запроса.
3. При неопределённом результате прочитать актуальное состояние записи.
4. Сравнить желаемое и текущее состояние.
5. Повторить изменение только если оно всё ещё требуется.
6. Зафиксировать нормализованный итог.

Exactly-once между MAX и Dikidi невозможно гарантировать без общего транзакционного механизма обеих платформ. Целевая гарантия формулируется как at-least-once delivery с идемпотентной бизнес-обработкой.

## 13. Redis и durable state

В референсной реализации Redis 7 используется для:

- polling ownership;
- polling marker;
- inbound event leases;
- completed-event dedupe;
- outbound jobs;
- outbound claims;
- retries;
- acceptance receipts;
- dead letter;
- rate limiting;
- health-related runtime state.

Критические переходы должны быть атомарными.

Если Redis недоступен:

```text
stop new poll batches
stop webhook claims
stop outbound claims
health = degraded / recovering
resume only after durable state recovers
```

Обработка без marker, leases и dedupe state считается небезопасной.

В промышленной инфраструктуре Redis может быть заменён внутренним state store Dikidi, если он обеспечивает те же атомарные и временные семантики.

## 14. Graceful shutdown

Runtime должен реагировать на:

- `SIGTERM`;
- `SIGINT`;
- platform abort signal.

Последовательность:

```text
1. health → stopping
2. остановить новые polls
3. остановить новые queue claims
4. дождаться активной работы или безопасно освободить leases
5. сохранить допустимое terminal state
6. health → stopped
```

Канонический timeout завершения составляет 30 секунд. Превышение timeout должно завершать процесс с ненулевым результатом и операторским событием.

## 15. Безопасность и персональные данные

### 15.1. Self-contact

Контакт принимается только через штатный механизм MAX.

Проверяется соответствие пользователя контакта отправителю.

Это уменьшает риск:

- ошибки в номере;
- просмотра чужих записей;
- перебора клиентской базы;
- передачи контакта третьего лица как собственной идентичности.

### 15.2. Least privilege

Интеграционный gateway получает только права, необходимые для клиентского сценария:

- поиск записей по подтверждённому телефону;
- чтение ограниченного набора данных визита;
- подтверждение;
- запрос переноса;
- запрос отмены.

Доступ к финансам, сотрудникам, настройкам компании и административным операциям не требуется.

### 15.3. Секреты

MAX token, Dikidi credentials и внутренние ключи:

- не хранятся в репозитории;
- не входят в runtime identity;
- не записываются в logs;
- разделяются между sandbox, pilot и production;
- ротируются без изменения application handlers;
- передаются через принятый Dikidi secret-management механизм.

TLS verification должна оставаться включённой.

### 15.4. Логи

Runtime logs являются структурированными техническими событиями.

Допустимые поля:

```text
event_id
job_id
component
event_name
operation_type
error_class
attempt
latency
result_status
technical company ID
```

Запрещённые поля:

```text
bot tokens
API credentials
phone numbers
personal names
message bodies
raw contacts
raw MAX updates
raw Dikidi payloads
secret URLs
```

### 15.5. Audit trail

Для изменяющей операции может храниться минимальный след:

```text
actor MAX user ID
appointment technical ID
requested action
accepted_at
idempotency key
normalized Dikidi result
client response status
```

Audit не должен дублировать полную клиентскую карточку или текст сообщения.

## 16. Первое сообщение и документы пользователя

Пример структуры:

> Добро пожаловать в клиентский сервис Dikidi в MAX. Здесь можно посмотреть предстоящие записи, получить напоминание и сообщить о подтверждении, переносе или отмене визита.
>
> Для поиска записей потребуется передать подтверждённый номер телефона, связанный с вашей учётной записью MAX.
>

Ссылки размещаются обычными гиперссылками в тексте.

Отдельные кнопки для юридических документов не используются.

Единственная функциональная кнопка этого шага:

```text
Передать номер телефона
```

Необходимость хранения версии документов и момента согласия определяется внутренними требованиями Dikidi. Архитектура допускает это состояние, но не навязывает отдельный реестр без необходимости.

## 17. Развёртывание в инфраструктуре Dikidi

Целевая официальная модель:

```text
Dikidi infrastructure
├── MAX client bot
├── transport runtime
├── integration gateway
├── durable state / queues
├── observability
└── internal API connectivity
```

Мы передаём:

- исходный код;
- архитектурное описание;
- платформенные контракты;
- conformance tests;
- инструкции развёртывания;
- recovery runbooks;
- перечень ограничений.

Dikidi самостоятельно:

- проводит внутренний аудит;
- адаптирует стек;
- управляет secrets;
- определяет data retention;
- подключает monitoring и alerts;
- масштабирует компоненты;
- сопровождает интеграцию.

Развёртывание внутри Dikidi:

- не создаёт отдельный внешний SaaS-контур;
- не требует постоянной передачи полной бизнес-базы третьей стороне;
- сокращает число участников обработки;
- позволяет использовать действующие политики безопасности;
- оставляет управление доступами и сроками хранения у владельца платформы;
- не требует постоянного доступа автора пилота после передачи.

Внутренний аудит и юридическая проверка всё равно выполняются по правилам Dikidi. Архитектура лишь уменьшает объём дополнительных согласований по сравнению со сторонним сервисом.

## 18. Наблюдаемость

### 18.1. Health states

Минимальные состояния:

```text
healthy
­degraded
```

## 19. Изоляция нагрузки и масштабирование

Промышленный контур должен поддерживать:

- per-user rate limits;
- per-company limits;
- per-branch limits при наличии устойчивой branch identity;
- отдельный concurrency для read и write operations;
- global limits API Dikidi;
- backpressure;
- queue age alerts;
- защиту от repeated button clicks;
- circuit breaker для длительно недоступного API;
- bulkhead isolation проблемной компании;
- autoscaling workers по глубине очереди.

Одна проблемная компания не должна блокировать остальных.

Один пользователь не должен бесконечно создавать одинаковые изменяющие операции.

Read operations и write operations рекомендуется разделять по concurrency и retry policy.

## 20. Технологический стек

### 20.1. Текущий пилот

- TypeScript client bot;
- Python API;
- Redis;
- PostgreSQL для пилотной зеркальной модели и технических данных;
- long polling.

### 20.2. Пилот с официальным API

- существующий transport runtime;
- тонкий integration gateway;
- Redis либо внутренний эквивалент;
- минимальное хранилище MAX identities и audit state;
- официальный API Dikidi;
- long polling на первом этапе;
- webhook как согласованный следующий этап.

### 20.3. Промышленная реализация

Возможны:

- сохранение TypeScript и Python;
- перенос runtime и gateway на Go;
- реализация на внутреннем стеке Dikidi;
- замена Redis и PostgreSQL внутренними платформенными компонентами.

Выбор языка должен основываться на:

- существующей компетенции команды;
- внутренних deployment standards;
- observability stack;
- API limits;
- модели масштабирования;
- latency requirements;
- стоимости эксплуатации.

Go может снизить runtime overhead и упростить масштабирование большого числа concurrent operations, но сам язык не заменяет durable state, idempotency, fencing и recovery contracts.

## 22. Границы гарантий

Архитектура утверждает:

- существует работающий пилотный контур;
- проверена глобальная идентификация по телефону;
- транспорт отделён от продуктовой логики;
- события защищены от повторной обработки;
- исходящие сообщения создаются через durable queue;
- временные ошибки обрабатываются bounded retries;
- постоянные ошибки изолируются;
- текущая реализация может перейти на официальный API;
- целевая схема не требует постоянной внешней копии всей бизнес-БД;
- решение может быть развёрнуто внутри инфраструктуры Dikidi;
- webhook evolution архитектурно предусмотрена.

Архитектура не утверждает:

- что известна внутренняя физическая схема БД Dikidi;
- что текущий Python API является окончательным промышленным сервисом;
- что webhook уже реализован в пилоте;
- что `accepted_by_max` означает прочтение;
- что exactly-once гарантирован между MAX и Dikidi;
- что заранее известна нагрузка всей клиентской базы;
- что внутренний аудит Dikidi не потребуется;
- что текущий пилотный endpoint является официальным публичным API;
- что текущая PostgreSQL-модель должна использоваться в production.
